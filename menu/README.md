# TC264 菜单示例使用说明
=

> 本文档描述的是 TC264 示例工程里的用法（含 `menu_app.c` 的硬件适配与示例页）。
> 在公开仓库里：核心与示例在 `menu/`，主机回归测试在 `tests/`；文中出现的
> `code/menu/...`、`user/cpu0_main.c`、`libraries/...` 都是那个示例工程里的路径。
## 一、先学会操作

| 当前状态 | 旋转编码器 | 短按编码器 | 长按编码器 |
| --- | --- | --- | --- |
| 浏览菜单 | 逆时针上移，顺时针下移 | 进入子页、进入参数编辑或执行选中动作 | 返回上一级 |
| 编辑参数 | 修改当前值 | 多档步长参数切换步长 | 确认并退出编辑 |

底部状态栏用于区分浏览和编辑状态；编辑数值时可查看当前步长。
单档步长参数没有其他档位可切换，开关和枚举也不按数值步长编辑。
菜单到达首尾时允许循环；内容超过可见行数时自动滚动。

注意：参数在旋转时就修改了，长按不是撤销操作，也不负责掉电保存。
摄像头参数通过后台提交，长按退出编辑不等于硬件已经写入成功，需结合状态条判断。

### 基础示例

| 菜单项 | 含义 | 当前配置 |
| --- | --- | --- |
| Enabled | 开关示例 | 关闭或开启，仅修改演示变量 |
| Count | 整数示例，不是动作执行次数 | 默认 25，范围 0～1000，步长 25／100／250 |
| Gain | 浮点数示例，不是摄像头模拟增益 | 默认 1.25，范围 0～20，步长 0.01／0.1／1／10 |
| Mode | 枚举示例 | 显示 OFF／LOW／HIGH／AUTO，对应实际值 0／2／7／42 |
| Save | 保存动作演示 | 仅把内部保存标志置为 1，没有写入掉电存储 |
| Count Action | 动作回调演示 | 每执行一次，内部动作计数加 1；当前页面不直接显示该计数 |

首页和实时状态页中的保存、计数动作使用相同回调。
不要把“按了保存”理解为已经保存全部菜单参数；真实项目需要自己实现存储和上电加载。

### 实时状态示例

- 启动（Start）：进度从 0 开始递增，到 100 后自动停止。
- 取消（Cancel）：停止进度更新。
- 运行中不允许返回上级；取消或完成后才能返回。
- 重新进入页面时，运行状态和进度重置。
- 进度是模拟任务，不代表正在控制电机或执行真实业务。
- 状态文字和进度条按变化更新，不应每次清空整个页面。
- Ticks / Progress 是实时数值行（`MENU_LIVE_VAR`）：不写任何回调，值变化时
  核心只重画这一行。Ticks 每 10 ms 加一，是刻意的持续刷新演示。
- 首页的 Uptime 也是实时数值行，且首页 `hooks` 为 `NULL`：说明普通列表页
  同样能实时刷新，不需要实时视图区。

### 实时数值演示页

“Live Values” 页用四行示范实时数值行的代表性写法，一屏就能看懂怎么加自己的
实时参数。页面用一个 `tick` 推进演示值，`view_height` 为 0（不申请实时视图
区），因此它同时示范了“只有 tick、没有视图区”的实时页写法。

| 行 | 示范什么 | 预期表现 |
| --- | --- | --- |
| GyroZ | 浮点 + 小数位数 + 单位（陀螺仪、PID 输出这类值的标准写法） | 形如 `GyroZ: -123.4dps`，持续变化 |
| Level | u8 整数 + 单位 | 0 ~ 100，每 0.5 秒变一次，形如 `Level: 42%` |
| State | 枚举显示标签，不是原始数字 | IDLE / RUN / FAULT 每 3 秒切换 |
| Step | 可编辑参数与实时行共存 | 短按进入编辑、旋转改值时，上面三行继续刷新 |

上面三行都用 `MENU_LIVE_VAR` 直接绑定变量；用 read 回调取值的写法见首页的
`Uptime` 行（`MENU_LIVE`），枚举标签的写法见 `State` 行（`MENU_LIVE_ENUM`）。
真实项目把 `g_live_*` 换成自己的快照变量即可，一行一个参数。

注意：这里的值都由时间派生，只用于示范显示行为，不代表任何真实业务量。
验证"不刷新"同样重要：把编码器停在任意一行，屏幕上不应有整页闪烁或残影。

## 三、摄像头测试页

配置和菜单定义集中在 `menu_app.c` 顶部，回调实现放在后面。
采集默认值在 `libraries/zf_device/zf_device_mt9v03x.h` 的
`MT9V03X_FPS_DEF`，固定为已实测图像正常的 **200 FPS**。
原始图像是 188×120 灰度，LCD 等比例放大到 240×153。

| 菜单项 | 用途 | 范围 / 步长 | 是否改摄像头 |
| --- | --- | --- | --- |
| 曝光（Exposure） | 曝光目标值，越大通常越亮、运动拖影也可能更明显；默认 512 | 1~4095；1/10/100 | 是，后台提交实时曝光命令 |
| 模拟增益（Analog Gain） | 放大传感器信号，提高亮度，也可能放大噪声；默认 32，约 2 倍 | 16~64；1/4/8，约 1~4 倍 | 是，后台写 0x35 |
| 黑白预览（Binary） | 关闭时显示灰度，开启时显示黑白图；默认关闭 | 关闭／开启 | 否 |
| 阈值（Threshold） | 黑白预览开启时，小于该值显示黑，否则白；默认 128 | 1~255；1/5/20 | 否，不修改原始图像 |
| 预览帧率（LCD FPS） | 预览刷新率上限，默认 50；实际可能更低 | 5~60；5 | 否，采集仍为每秒 200 帧 |
| 冻结（Freeze） | 停止更新屏幕图像，方便观察；默认关闭 | 关闭／开启 | 否，采集和帧率统计继续 |

操作：旋转选择项，短按进入编辑；旋转改值；编辑中短按切换步长；
长按退出编辑，再长按返回上级；长按不是撤销，也不是等待硬件写入成功。
Exposure / Analog Gain 旋转时立即更新屏幕目标值，后台合并中间值，
两项合计最多每 100 ms 启动一次写入；已提交的事务完成后继续提交最新目标。
其他预览参数仍即时生效。离开页面后，已接受的写入请求继续完成。
图像下方有四行参数位置，继续向下旋转即可滚动到 LCD FPS / Freeze。
冻结期间调整参数不会改变已冻结图像；解除冻结后显示最新图像。
重新进入页面自动解除冻结，其他参数在本次上电期间保留。

状态条独立于图像，按变化字符覆盖，不随每帧图像重画：

- CAM：DMA 成功完成的帧数 / 秒，不是传感器 VSYNC 数，也不是算法处理帧率。
- LCD：实际调用预览绘图的次数 / 秒，不等于液晶面板物理刷新率。
- RUN / HOLD：预览运行 / 冻结。冻结约一秒后 LCD 降到 0，CAM 继续更新。
- LOST：连续 250 ms 未观察到新的 DMA 完整帧，覆盖 RUN / HOLD，并显示 CAM 0。
  检查独立于当前页面和 Freeze；新完整帧到来后自动恢复，重新进页不清除断流状态。
  这是断流提示，不是丢帧计数；判断与显示仍受主循环调度延迟影响。
- OK / WAIT / ERR / INIT：参数无未完成请求或已知写入错误 / 参数待写入或写入中 /
  有参数写入失败 / 摄像头初始化失败。优先级为 INIT > ERR > WAIT > OK。
  OK 只表示写参状态，采集健康看 RUN / HOLD / LOST。
  写入错误按曝光、增益分别保留，仅该项后续成功写入才清除，不被另一项成功掩盖。
  ERR 时保留目标值，不能当作已生效；没有新修改时不自动重试。
  重新旋转该项可提交新请求，ERR 在成功前仍保留。参数读写不触发摄像头重初始化。

注意：曝光和增益显示的是用户目标值，不是寄存器实测回读。
WAIT / ERR 时不能认为目标已生效；没有 WAIT / ERR 也仅说明接口接受了请求。
底层可能钳位曝光，不能把 512 当作 512 微秒。
增益寄存器参考 [OpenMV MT9V0xx 定义](https://github.com/openmv/openmv/blob/master/drivers/sensors/mt9v0xx.h)
中的 `ANALOG_GAIN=0x35`、范围 16~64；当前沿用默认手动曝光/增益配置。
用户已实机确认摄像头参数能够实时调整；这不等于已逐个回读寄存器或验证全部参数极限。

本页不保存到 Flash；原示例的 Save 只是演示动作，不保存摄像头参数。
自动曝光/自动增益、FPS、分辨率、图像偏移和 PCLK 不作为实时编辑项：
需要先明确模块型号、配置接口以及重初始化边界，不能只绑定变量就声称生效。
200 FPS 图像正常不代表已验证零丢帧；258 FPS 拼接问题尚未通过
VSYNC/DMA 丢帧计数和缓冲区时序定位，不应把旧注释中的 3.8 ms 当作硬上限。

运行时写参边界：UART 的寄存器地址间隔及回复超时改为分步轮询，
不再通过 `system_delay_ms()` 等待；收包使用三字节回复缓冲，数据中的
0xA5 不再误当作新的帧头。原四字节 UART 发送仍同步（9600 baud 下线速约 4.2 ms），
SCCB 仍调用原厂 `zf_device_config.a` 中的同步函数，单次耗时需实测。
这不是完全无阻塞的通信驱动；已消除的是菜单逐步积压写入和 UART 长回复等待。
菜单使用完整 STM 计数转换的毫秒时间，避免原短计时器约 43 秒回绕引发误超时。

### 增加一个参数，只需三步

以增加一个“目标值”整数参数为例，代码名称保留英文，解释全部用中文。
当前屏幕使用 8×16 字体，以下示例沿用现有英文标签；文档中文化不等于屏幕已支持中文字库。

1. 在顶部业务变量区增加变量，名称不要与已有变量重复：

   ```c
   static uint16_t g_target = 100U; // 实际被菜单修改的变量，上电默认值为 100
   ```

2. 在步长数组区增加该参数自己的档位：

   ```c
   static const double g_target_steps[] = { 1.0, 10.0, 50.0 }; // 三档步长
   ```

3. 在已有页面的开始和结束宏之间增加一项，注意相邻项用逗号分隔：

   ```c
   MENU_U16_STEPS("Target", &g_target, 0, 1000, g_target_steps, 3U),
   ```

这一行依次表示：屏幕名称、变量地址、最小值、最大值、步长数组、档位数量。
`MENU_U16_STEPS` 要配 `uint16_t` 变量；不要随意混用不同类型。
每个参数可以有自己的步长数组和档位数量，互不要求相同；数组有几项，最后的数量就写几。
这些步长大小在代码中配置，旋钮只切换已经配置的档位，不是在屏幕上重新定义档位大小。
普通变量绑定只修改内存；需要发送硬件命令时，参考摄像头的 `MENU_BIND_STEPS` 读写回调。

### 显示一个实时数值怎么理解

陀螺仪、PID 输出、编码器速度这类值用 `MENU_LIVE` / `MENU_LIVE_VAR` 做成
“实时数值行”：只读，值变化时菜单核心只重画这一行，其它行不重画。

```c
MENU_LIVE_VAR("GyroZ", MENU_VALUE_FLOAT, &g_gyro_z_dps, 1U, "dps"), /* 直接绑定变量 */
MENU_LIVE("LoopHz", MENU_VALUE_U32, read_loop_hz, NULL, 0U, "Hz")   /* 值来自只读回调 */
```

- 第一个写法绑定变量地址，第二个写法用 `read` 回调取值（需要换算、取快照或
  跨核同步时用）。
- 浮点用倒数第二个参数控制小数位数，最后一个参数是数值后的单位文本，
  不需要就填 `NULL`。
- 这两行放在普通页里就行，**不需要**写 `enter/tick/draw/update/is_dirty`，
  也不需要应用自己请求重绘。
- 枚举型实时值用 `MENU_LIVE_ENUM`，显示 `enum_labels` 里匹配的标签；实际值
  不在列表里时退化成显示原始数字。
- 取值失败（`read` 回调返回 `false`）时该行显示 `?`：从"有值"变成"取不到"
  会触发一次重画，不会把过期旧值留在屏幕上冒充实时数据。
- 它是只读项：短按不会进入编辑，旋转到它不会改值；写操作请用 `MENU_*_STEPS`
  或 `MENU_BIND_STEPS`。

刷新口径与代价：

- 每个 `menu_tick` 比较一次**可见**实时行的原始值，只有值变了才请求重画该行；
  值没变时不格式化文本、不碰屏幕。
- 比较原始值而不是格式化后的字符串，因此不存在“值没变还每帧做浮点
  `snprintf`”的开销；浮点按位比较，NaN 不会被误判成每帧都在变化。
- 菜单核心不做字符差分；真正只推送变化像素的是显示适配层的 `row` 回调
  （见 `tc264_row`），所以“几个数字在跳”的 SPI 代价很小。
- 刷新上限由 `MENU_TICK_PERIOD_MS`（默认 10 ms）和主循环周期决定；持续变化的
  行越多，格式化开销越大（浮点格式化是这条链路上最贵的一步）。
- 刷新由“原始值变化”触发，不是由“显示文本变化”触发：显示 1 位小数却绑定
  毫秒值时，这一行会按 100 Hz 重画。**绑定前先量化到显示分辨率**（首页
  `demo_read_uptime` 就是先量化到 0.1 秒再返回），需要高频刷新时才返回原始值。
- 缓存行数由 `MENU_MAX_LIVE_ROWS`（默认 16）决定，需覆盖当前屏幕的可见行数；
  超出缓存范围的行不会自动刷新，只能在整屏重画时更新。
- 实时数值行与实时视图区可以同页共存：视图局部刷新和行刷新在同一帧完成。
- 高频噪声信号建议先在业务侧滤波或降采样，再放进实时数值行，避免把显示
  刷新率当成采样率使用。
- `read` 回调每个 `menu_tick` 都会被调用一次，必须非阻塞，且不要在里面做
  硬件等待；推荐业务侧先采样成快照变量，再用 `MENU_LIVE_VAR` 绑定。
  跨核共享的快照是否已经可见、是否需要同步，需要按芯片内存模型单独确认。

### 增加一页怎么理解

- `MENU_PAGE_BEGIN` 与 `MENU_PAGE_END` 包住一页，中间一行就是一个菜单项。
- 先定义子页，再在父页增加 `MENU_SUBMENU` 指向它，即可从父页进入。
- 开关用 `MENU_BOOL`，数值用对应类型的宏，枚举用 `MENU_ENUM`，动作用 `MENU_ACTION_CTX`。
- 普通页结束宏的第三个参数填 `NULL`，不用写实时页面函数。

### 页面扩展功能是什么

把它理解成“菜单在特定时刻自动帮你调用的函数”，不是每个页面都必须实现。
普通参数列表不需要它；想在上半屏画图、下半屏调参，就参考摄像头页的 `g_camera_view_hooks`。

| 扩展接口 | 直白解释 |
| --- | --- |
| `enter` | 刚进入页面时做准备，例如清零本页统计 |
| `tick` | 页面运行期间定期处理，例如检查新图像、更新进度 |
| `draw` | 页面需要完整绘制视图区时，画出初始内容 |
| `event` | 页面想单独处理按键时使用，普通操作可交给菜单默认处理 |
| `can_leave` | 返回前问一下业务是否允许离开，例如任务运行中禁止返回 |
| `leave` | 真正离开时收尾 |
| `user` | 传给这些函数的自定义数据地址，不需要时填 `NULL` |
| `view_height` | 实时视图区占多高，剩余空间自动留给参数列表 |
| `update` | 页面运行中只重画变化部分，不清空整个视图区 |
| `is_dirty` | 告诉菜单当前有没有变化，没有变化就不触发视图区更新 |

新增实时页面时，同时设计“首次画完整内容”和“后续只更新变化内容”。
普通实时更新只刷新变化区域；切页时还必须覆盖旧页多余内容，不能为了少刷新而留下残影。
摄像头图像区按预览节拍绘制图像，状态文字独立按变化字符更新，不做图像逐像素差分比较。

### 实时页是怎么跑起来的

先建立心智模型，再看代码就顺了：

**你只负责“更新数据 + 画”，菜单核心负责“什么时候调你”。**

核心的周期入口是 `menu_tick()`（在 `menu.c` 里），每一帧的顺序是固定的：

1. 页面栈里每一层的 `tick` 都调一遍（先父页，后当前页）；
2. 调当前页的 `tick`，紧接着问 `is_dirty`：这一帧有变化吗；
3. 扫描实时数值行（`MENU_LIVE` 那些），值变了的行标脏；
4. 只要有任何重画请求，就进 `menu_render()` 真正往屏幕上写。

`draw` 和 `update` **不是你自己调的**，是 `menu_render()` 按情况调的：

| 这一帧的情况 | 核心做什么 |
| --- | --- |
| 刚进页面、切页面、有人请求整屏重画 | 清掉实时区，调你的 `draw` |
| 只是“有变化”（`is_dirty` 返回 true） | 调你的 `update`（没写 `update` 就退回清块 + `draw`） |
| `is_dirty` 返回 false | 实时区一个像素都不写 |

所以 `draw` 一辈子只跑几次（进页面那一下），`update` 才是每帧跑的那个。

四个必需回调各自回答一个问题：

| 你的代码 | 回答什么 | 什么时候被调 | 写错会怎样 |
| --- | --- | --- | --- |
| `tick` | 数据该更新了吗 | 每次 `menu_tick`（默认 10 ms 一次） | 不写就等于这页永远不周期刷新 |
| `is_dirty` | 屏幕上的内容过时了吗 | 每次 tick 之后 | 不写（或永远返回 true）＝ 每帧都刷，白费 SPI |
| `draw` | 这页完整长什么样 | 进页面 / 整屏重画时 | 只画静态不画数值 → 第一帧缺数字 |
| `update` | 哪一小块变了 | `is_dirty` 为 true 的那些帧 | 坐标和 `draw` 不一致 → 数字画到别处 |

把下面教程里的“电机页”按帧拆开看（`tests\realtime_page_example.c`
跑出来的就是这套行为）：

| 时刻 | `tick` 里发生了什么 | 核心的判断 | 屏幕上的动作 |
| --- | --- | --- | --- |
| t=0 第一帧 | rpm=0、duty=0 | 进页面第一帧，整屏重画 | 调 `draw`：边框、标签、两个字段、参数行落在 y=100 |
| t=0 再来一帧 | 值没变 | `is_dirty` 比较上次文本 → false | 零次绘制，屏幕纹丝不动 |
| t=10 | rpm=1、duty 仍 0 | `is_dirty` → true | 调 `update`：只重画 rpm，duty 一个像素没碰 |
| t=100 | rpm=10、duty=1% | `is_dirty` → true | `update` 里两个字段各画一次，没有多余重画 |

三个和“什么时候被调”有关的坑，记住能省很多时间：

- 不写 `tick` 就等于关掉了这一页的周期刷新（核心只在 `tick` 存在时才去问 `is_dirty`）。
- `draw` 里也要画动态字段：第一帧只走 `draw`，不补的话数字要等第一次变化才出现。
- `is_dirty` 返回 false 的帧，`update` 根本不会执行——别把必须做的事只写在 `update` 里。

两个和“布局、范围”有关的：

- `view_height` 决定实时区高度，参数行自动排在它下面（本工程标题 40 像素、实时区 60 像素 → 参数行在 y=100）。
- 进了子页，父页的 `tick` 仍然每帧在跑（核心是按页面栈逐层调的）。

最后分清两条路：列表行里的实时数值（`MENU_LIVE` 系列）走的是**另一条路**——
核心自己扫描、自己重画，不需要这一节的任何回调；只有要自己画图（进度条、
波形、图像）、要跑页面状态机、要接管按键，才需要实时页。

### 自己做一个实时页（从零开始）

先判断要不要实时页：

| 你想要的 | 该用什么 |
| --- | --- |
| 只显示几个会变的数值 | `MENU_LIVE` / `MENU_LIVE_VAR`，一行搞定，本节不用看 |
| 上半屏画图或大字，下半屏照常调参 | 实时页（本节） |
| 页面自己跑状态机、要接管按键、运行中不许返回 | 实时页 + `event` / `can_leave` |

实时页就是让页面的第三个参数不再是 `NULL`，而是一张钩子表。最小骨架四个回调：

- `tick`：推进业务状态。**必须有**——核心靠它决定这一页要不要周期刷新。
- `draw`：首帧把实时区的静态内容（边框、标签）画一遍。
- `is_dirty`：没有变化就返回 `false`，这一帧核心什么都不刷。
- `update`：只重画变化的那一小块，别整块清掉重画。

下面是一个完整可跑的“电机页”：上面 60 像素实时区显示 RPM 和占空比，下面照常
放一个可编辑参数。把这段贴进 `menu_app.c` 的页面定义区就行（`stdio.h` 和
`string.h` 顶部已经 include 过）。

```c
/* 本页业务变量：真实项目里由采样 / PID 更新，这里按时间派生 */
static uint16_t g_motor_rpm;
static uint8_t  g_motor_duty;
static uint16_t g_motor_target = 50U;
/* “屏幕留底”：这两份内存里存的就是屏幕上此刻显示的那两串字。
 * is_dirty 拿它比较来判断要不要重画，update 画完顺手把它更新成新文字。 */
static char g_motor_rpm_text[8];
static char g_motor_duty_text[8];

/* 把两个值翻译成“屏幕上要显示的那串字”，并顺手更新“屏幕留底”：
 * g_motor_rpm_text / g_motor_duty_text 存的就是屏幕上此刻显示的文字，
 * is_dirty 拿它做比较，决定这一帧要不要重画。
 *
 * 格式串写成定宽（%4u / %3u%%）：位数不够用空格补齐，每次写出去的都是
 * 同样宽的字符格，屏幕上直接覆盖旧字，不需要字符差分，也不会留残影。
 *
 * 只在真要画的时候调它（draw / update）。is_dirty 里必须用临时缓冲区格式化
 * 再比较——那里如果也调这个函数，留底会被提前改掉，比较永远相等，
 * 屏幕就再也不会刷新。 */
static void motor_format_values(void)
{
    /* (void) 是显式忽略 snprintf 的返回值；sizeof(数组) 让缓冲区改大小时不用改这里 */
    (void)snprintf(g_motor_rpm_text, sizeof(g_motor_rpm_text), "%4u", (unsigned)g_motor_rpm);
    (void)snprintf(g_motor_duty_text, sizeof(g_motor_duty_text), "%3u%%", (unsigned)g_motor_duty);
}

/* 1) 周期任务：每次 menu_tick 调一次；必须非阻塞，只推进一步 */
static void motor_tick(void *user, uint32_t now_ms)
{
    (void)user;
    g_motor_rpm = (uint16_t)((now_ms / 10U) % 3000U);
    g_motor_duty = (uint8_t)((now_ms / 100U) % 101U);
}

/* 2) 首次完整绘制：实时区的静态内容（边框、标签）在这里画 */
static void motor_draw(void *user, MenuCanvas *canvas)
{
    (void)user;
    menu_canvas_rect(canvas, 0U, 0U, (uint16_t)(canvas->width - 1U), (uint16_t)(canvas->height - 1U));
    menu_canvas_text(canvas, 4U, 6U, "RPM");
    menu_canvas_text(canvas, 4U, 26U, "DUTY");
    motor_format_values();
    menu_canvas_text(canvas, 60U, 6U, g_motor_rpm_text);
    menu_canvas_text(canvas, 60U, 26U, g_motor_duty_text);
}

/* 3) 脏检查：返回 false 时核心这一帧什么都不刷 */
static bool motor_is_dirty(void *user)
{
    char text[8];
    (void)user;
    (void)snprintf(text, sizeof(text), "%4u", (unsigned)g_motor_rpm);
    if (0 != strcmp(text, g_motor_rpm_text)) return true;
    (void)snprintf(text, sizeof(text), "%3u%%", (unsigned)g_motor_duty);
    return 0 != strcmp(text, g_motor_duty_text);
}

/* 4) 局部更新：哪个字段变了就重画哪个，没变的连碰都不碰 */
static void motor_update(void *user, MenuCanvas *canvas)
{
    char text[8];
    (void)user;
    (void)snprintf(text, sizeof(text), "%4u", (unsigned)g_motor_rpm);
    if (0 != strcmp(text, g_motor_rpm_text))
    {
        (void)snprintf(g_motor_rpm_text, sizeof(g_motor_rpm_text), "%s", text);
        menu_canvas_text(canvas, 60U, 6U, text);
    }
    (void)snprintf(text, sizeof(text), "%3u%%", (unsigned)g_motor_duty);
    if (0 != strcmp(text, g_motor_duty_text))
    {
        (void)snprintf(g_motor_duty_text, sizeof(g_motor_duty_text), "%s", text);
        menu_canvas_text(canvas, 60U, 26U, text);
    }
}

/* 5) 钩子表：编号顺序不能改（这是结构体初始化，不是命名赋值） */
static const MenuPageHooks g_motor_hooks = {
    NULL,           /*  1 enter       进页面要重置状态时才写 */
    motor_tick,     /*  2 tick        必须有：核心靠它决定这一页要不要周期刷新 */
    motor_draw,     /*  3 draw        首帧画静态内容 */
    NULL,           /*  4 event       要自己接管按键时才写 */
    NULL,           /*  5 can_leave   运行中不许返回时才写 */
    NULL,           /*  6 leave       离页要停机 / 恢复中断时才写 */
    NULL,           /*  7 user        没有额外上下文 */
    60U,            /*  8 view_height 实时区高度：参数行自动排在它下面 */
    motor_update,   /*  9 update      只刷变化的部分 */
    motor_is_dirty  /* 10 is_dirty    没有变化就不刷 */
};

/* 6) 页面：上面是实时区，下面照常写参数行 */
MENU_PAGE_BEGIN(g_motor_page, "Motor")
    MENU_U16("Target", &g_motor_target, 0, 1000, 10)
MENU_PAGE_END(g_motor_page, "Motor", &g_motor_hooks);
```

要点：

1. **定宽文本**：`%4u` / `%3u%%` 这种定宽格式，位数变了用空格补齐，屏幕上直接
   覆盖旧字——既不用写字符差分，也不会留残影。浮点值先量化到显示精度再格式化。
2. **`update` 里逐字段比较**：哪个变了画哪个，没变的连碰都不碰；`draw` 和
   `update` 里同一个字段的坐标必须一致（这里是 `(60,6)` 和 `(60,26)`）。
3. **`view_height` 会挤掉参数行**：实时区 60 像素，参数行就从标题下面 60 像素
   开始排（本工程标题 40 像素，所以那行在 y=100）。
4. 用到时才补：`event`（自己接管按键）、`can_leave`（运行中不许返回）、
   `leave`（离页停机或恢复中断）、`enter`（进页清零统计）。
5. 钩子表的**顺序不能改**：它是结构体初始化，不是命名赋值，写错位置编译器不报错。

要画条形图、图像、状态条的写法，见本工程两个现成实现：`Live State` 页
（进度条 + 状态文字按字符差分，`g_demo_view_hooks`）和 `Camera Test` 页
（实时图像 + 独立状态条，`g_camera_view_hooks`）。

本节的示例代码是被编译并跑过的：`tests\realtime_page_example.c` 里是
同一份代码加 8 条行为断言，`run.ps1` 会自动比对两边是否一致，不一致直接报错。

两个容易踩的约定：

- 页面钩子的 `tick` 是实时刷新的开关：只实现 `update` / `is_dirty` 而不实现
  `tick`，菜单核心不会为这个页面做周期刷新。
- 实时视图区以外的列表行不会因为外部变量变化而自动重画；需要自动刷新就用
  `MENU_LIVE` / `MENU_LIVE_VAR`，或者由页面自己在 `tick` 里请求重绘。

菜单核心还提供有符号整数、只读项、实时数值项和自定义项等接口
